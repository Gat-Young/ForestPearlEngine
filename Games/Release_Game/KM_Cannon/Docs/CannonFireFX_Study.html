2엔진 렌더 패스 (MeshRenderPass)

게임 코드는 그리기 명령을 직접 내리지 않는다. 컴포넌트가 RenderItem(포인터 묶음)을 등록하면, 렌더러가 매 프레임 값을 복사해 정렬 후 그린다.

왜 Priority 100 / 110 인가

불투명 물체는 기본 0. 반투명은 불투명을 다 그린 뒤 그려야 뒤 배경과 섞인다. 더하기 섬광(110)은 연기(100) 위에 얹어 밝게 보이도록 마지막.

3행렬 규약 · MVP

C++ DirectXMath는 행벡터 규약: v' = v · M, 합성은 왼쪽부터 World = S · R · T.

clip = v · World · View · Proj = v · WVP

엔진은 행렬을 전치하지 않고 그대로 올리고, HLSL은 기본 column_major로 읽는다. 메모리상 같은 16개 값을 열 우선으로 읽으면 전치된 행렬 Mᵀ가 된다.

HLSL mul(M, v) = Mᵀ · vᵀ = (v · M)ᵀ → C++ 의 v · M 과 같은 값

그래서 셰이더에서는 mul(mWVP, pos)처럼 행렬을 앞에 쓴다. (Cena 프로젝트는 D3DCOMPILE_PACK_MATRIX_ROW_MAJOR로 컴파일해서 mul(pos, mTM) 순서였다 — 같은 결과, 규약만 다름.)

카메라 위치 꺼내기

View는 월드 → 카메라 변환. 역행렬은 카메라 → 월드. 카메라 공간 원점 (0,0,0,1)을 역행렬로 보내면 월드의 카메라 위치.

Eye = (0,0,0,1) · View⁻¹ → HLSL : mul(mInverseView, float4(0,0,0,1)).xyz

= 역행렬의 4번째 행(이동 부분). Cena의 XMMatrixInverse(nullptr, g_mView).r[3]와 같은 개념.

4빌보드 수학

4-1. 보통 빌보드 (연기 · 정면 별)

Cena는 CPU에서 S · Rz · (View 회전)⁻¹ · T 월드 행렬을 만들었다. 이번엔 뷰 공간에서 같은 일을 한다.

q  = (u − 0.5, 0.5 − v) · Size.xy          // 판 모서리, 위가 +y
q  = Rot(θ) · q                              // 화면 안 회전 (Size.z)
Pv = mul(mWV, (0,0,0,1))                     // 판 가운데를 뷰 공간으로
Pv.xy += q                                   // 뷰 공간의 x,y = 화면 가로·세로
clip = mul(mProj, Pv)
Rot(θ) = [ cosθ −sinθ ; sinθ cosθ ]
왜 같은가 : 뷰 공간 축은 이미 카메라에 정렬돼 있다. 월드에서 “뷰 회전의 역”을 곱해 판을 세우는 것 = 뷰 공간에서 x,y 축으로 그냥 펼치는 것. 행렬 하나 덜 만들고 정점 셰이더에서 끝난다.

UV로 모서리를 만드는 이유 : Plane 메쉬의 정점 위치(XZ 평면인지 XY인지)에 의존하지 않는다. 메쉬가 어떤 방향이든 UV는 0~1.

4-2. 늘인 빌보드 (옆 불꽃 · Axis billboard)

판의 가로축을 진행 방향 r에 고정하고, 세로축만 카메라 쪽으로 돌린다. 레이저 · 총알 궤적 · 불꽃 기둥에 쓰는 기법.

r = Axis.xyz                       // 정규화된 진행 방향
c = normalize(Eye − C)
s = r × c ;  s /= |s|              // r, c 둘 다에 수직 → 판의 세로축
P = C + r·(q.x·Length) + s·(q.y·Width)
  • s ⟂ r 이므로 판은 r 방향으로 길쭉하게 유지된다.
  • s ⟂ c 이므로 판 평면(r, s)이 카메라 쪽 벡터를 최대한 포함 → 판의 법선 n = r × s 가 c와 가장 가깝게 정렬 (판이 카메라를 향함).
  • 퇴화 : 카메라가 r 방향으로 똑바로 보면 r ∥ c → |r × c| = 0. 판이 선이 되어 안 보임. 코드에서 len < 0.001이면 임의 축으로 대체. 그래서 정면 별(보통 빌보드)을 같이 그려서 어느 각도에서도 한쪽은 보이게 했다.
|r × c| = |r||c| sinθ → θ = r 과 시선 사이 각. θ→0 이면 판 폭 → 0

5블렌딩 · 깊이

출력 = Src(픽셀 셰이더 결과)와 Dest(이미 있는 색)의 섞기.

Out = Src · SrcBlend (BlendOp) Dest · DestBlend
연기 BS_FX_ALPHA섬광 BS_FX_ADD
설정SRC_ALPHA / INV_SRC_ALPHA / ADDONE / ONE / ADD
식Out = Cs·αs + Cd·(1 − αs)Out = Cs + Cd
의미덮기 (투명도만큼 가림)빛 더하기 (검정 = 0 = 안 보임)
순서중요 — 먼 것부터 그려야 정확무관 — 덧셈은 교환법칙
텍스처smoke4.dds (알파 채널 있음)jpg (알파 없음, 검정 배경)
세기 조절Color.aColor.rgb 에 곱함 (알파 안 씀)

알파 블렌딩이 순서에 민감한 이유

두 장 A(앞), B(뒤)를 배경 D 위에 섞을 때:

B→A : αA·A + (1−αA)(αB·B + (1−αB)·D) ≠ A→B : αB·B + (1−αB)(αA·A + (1−αA)·D)

앞에 있는 판을 나중에 그려야 앞 판이 뒤를 가리는 결과가 된다. 이번 구현은 연기끼리 정렬하지 않았다(ponytail 주석). 연기는 비슷한 회색이라 티가 적지만, 정확히 하려면 카메라 거리로 정렬해 Priority를 다시 준다 (Cena는 뷰 공간 z로 std::sort).

깊이 쓰기 끔 (DS_DEPTH_WRITE_OFF)

  • 깊이 테스트는 켬 : 배 · 대포 뒤에 있는 연기는 가려져야 한다.
  • 깊이 쓰기는 끔 : 반투명 판이 깊이를 쓰면, 뒤에 그려질 다른 연기 판이 깊이 테스트에서 탈락해 사각형 구멍이 생긴다.
AlphaToCoverage : 엔진 기본 BS_ADD는 이름과 달리 알파 섞기에 AlphaToCoverage가 켜져 있다. MSAA 4x에서 알파를 샘플 마스크로 바꿔 디더링 무늬가 생기므로, 부드러운 연기에는 끈 상태를 따로 만들었다.

6파티클 시뮬레이션

적분 (명시적 오일러)

p ← p + v·dt v ← v·drag + a·dt

a = 바람 (+X 0.3) + 부력 (+Y 0.3). 단순하고 빠르지만 dt가 크면 오차가 커진다 — 이펙트에는 충분.

공기 저항

v ← v·(1 − k·dt) ≈ v·e^(−k·dt) (k = 1.5 → 1초 후 약 22%)

(1 − k·dt)는 e^(−k·dt)의 1차 테일러 근사. FPS가 달라도 거의 같은 감속. max(…, 0)으로 dt가 큰 프레임에 속도가 뒤집히는 것을 막음. 더 정확히 하려면 expf(-k*dt).

수명 곡선 (t = Age / Life, 0→1)

값식모양
크기Size·(1 + 2.5t)선형으로 3.5배까지 퍼짐
알파min(5t, 1)·(1 − t)0.2초(정규화 t=0.2) 만에 최대 0.8, 이후 천천히 사라짐
색lerp(주황, 회색, min(1.5t, 1))불씨 → 연기
회전Rot += Spin·dt저마다 다른 각 · 회전 → 같은 그림 반복 티 감춤
lerp(a, b, t) = a + (b − a)·t

발사 버스트

12개를 포신 방향으로 Dir · Rand(1.5, 5) + 무작위 퍼짐. 빠르게 뿜어졌다가 저항으로 멈추고 부력 · 바람에 실려 올라간다. 섬광은 0.1초, 크기 1.5·(1.5 − 0.5k)로 꺼지며 살짝 커짐 (k: 1→0).

7소켓 · 쿼터니언

총구 = 대포 메쉬 JSON의 "Muzzle" 소켓에 SetupAttachment(Mesh, "Muzzle")로 붙인 빈 컴포넌트.

World.Scale = Parent.Scale ⊙ Socket.Scale
World.Rot = Parent.Q · Socket.Q
World.Pos = Parent.Pos + Rotate(Parent.Q, Socket.Pos ⊙ Parent.Scale)

(⊙ = 성분별 곱). 그래서 소켓 위치는 메쉬 로컬 = 0.33배 전 FBX 크기로 적는다.

방향 구하기

Dir = Rotate(Muzzle.Q, (0,0,1)) = q · v · q*

“총구 오브젝트의 앞(+Z)”을 월드로 돌린 것. 소켓 Rotation(오일러, 도)만 바꾸면 방향이 바뀐다.

왜 쿼터니언

  • 짐벌락 없음 (오일러는 두 축이 겹치면 자유도 1개 잃음)
  • 합성이 곱 한 번, 보간(slerp)이 매끄러움
  • 4개 값 — 3×3 행렬(9개)보다 작고, 정규화로 오차 보정이 쉬움

8섬광 빛 감쇠

I(d) = LightColor / (a + b·d + c·d²) (a, b, c) = (0, 0.1, 0.1), d > Range 이면 0
LightColor(t) = (1, 0.6, 0.2) · 5 · (남은 시간 / 0.3)
  • 세기 5 = 1을 넘는 순간 과다 노출 — 쏘는 순간 배 · 대포가 번쩍.
  • a = 0 이므로 d → 0 에서 무한대로 커짐. 총구 바로 앞 표면이 하얗게 날아가면 a를 조금 주면 된다.
  • 2차 항(c·d²)은 물리적인 역제곱 법칙, 1차 항(b·d)은 게임용 완화.

10개선 방향 (면접에서 “더 하면?” 대비)

  • 정렬 : 연기를 뷰 공간 z로 정렬 → Priority 재지정. 또는 순서 무관 투명(OIT, weighted blended).
  • 인스턴싱 : 지금은 판 1장 = DrawCall 1번 (최대 34번). 인스턴스 버퍼(위치 · 크기 · 색)로 1번에.
  • GPU 파티클 : Compute Shader로 시뮬레이션 + 간접 그리기(DrawInstancedIndirect) → 수만 개.
  • 소프트 파티클 : 깊이 텍스처와 비교해 지면 · 배와 만나는 경계를 부드럽게 (판이 물체를 자르는 직선 제거).
  • 시트 애니메이션 : 8×8 시트 UV = 시작 (f%8, f/8)/8, 크기 1/8 (Cena Param).
  • 오버드로 : 큰 반투명 판이 겹치면 픽셀 셰이더 비용 증가 → 개수 · 크기 · 해상도 조절.
  • Fill-rate vs 정점 : 파티클은 보통 정점보다 픽셀(채우기)이 병목.

11면접 질문

질문을 눌러 답을 보기 전에 먼저 소리 내어 답해 보세요.

빌보드란 무엇이고 어떻게 구현했나요?기본
항상 카메라를 향하는 판. 정점 셰이더에서 판 가운데를 뷰 공간으로 보낸 뒤, UV로 만든 모서리 오프셋을 뷰 공간 x,y에 더하고 투영했습니다. 뷰 공간 축이 이미 화면에 정렬돼 있으므로, CPU에서 뷰 회전의 역행렬을 곱하는 방식과 결과가 같고 행렬 계산이 줄어듭니다.
축 고정 빌보드는 어떻게 만들고, 어떤 한계가 있나요?수학
판 가로축을 진행 방향 r에 고정하고 세로축 s = normalize(r × c)로 둡니다(c는 카메라 쪽). s가 r과 c 둘 다에 수직이라 판이 길쭉함을 유지한 채 카메라 쪽으로 최대한 돌아갑니다. 카메라가 r 방향으로 정면에서 보면 r × c가 0이 되어 판이 선이 됩니다. 그래서 정면용 보통 빌보드를 함께 그려 보완했습니다.
알파 블렌딩과 더하기 블렌딩의 차이, 각각 언제 쓰나요?기본
알파: Cs·α + Cd·(1−α). 덮어서 가리는 연기 · 먼지 · 유리. 순서가 결과를 바꿈.
더하기: Cs + Cd. 빛 · 불꽃 · 섬광 · 마법. 교환법칙이 성립해 정렬이 필요 없고, 겹칠수록 밝아짐. 검정은 0이라 알파 채널 없는 jpg도 바로 쓸 수 있습니다.
반투명 물체는 왜 깊이 쓰기를 끄나요? 깊이 테스트는요?렌더링
테스트는 켜야 불투명 물체 뒤의 연기가 가려집니다. 쓰기를 켜면 먼저 그린 반투명 판이 깊이를 차지해, 그 뒤에 있는 다른 반투명 판이 테스트에서 탈락하고 사각형으로 잘려 보입니다. 그래서 불투명 → (정렬된) 반투명, 반투명은 쓰기 끔이 기본 순서입니다.
반투명 정렬은 어떻게 하나요? 정렬로 해결 안 되는 경우는?심화
카메라 거리(뷰 공간 z)로 먼 것부터 그립니다. 하지만 서로 관통하거나 교차하는 판, 오목한 메쉬 내부는 물체 단위 정렬로 해결되지 않습니다. 이때는 OIT(Weighted Blended, Depth Peeling, Per-pixel linked list)를 쓰거나, 더하기처럼 순서 무관한 섞기로 바꿉니다.
C++와 HLSL의 행렬 곱 순서가 왜 다른가요?수학
DirectXMath는 행벡터(v·M) 규약입니다. 엔진은 행렬을 전치 없이 그대로 올리고 HLSL은 기본 column_major로 읽어서, 셰이더 안에서는 전치된 행렬로 보입니다. (v·M)ᵀ = Mᵀ·vᵀ 이므로 mul(M, v)가 C++의 v·M과 같습니다. 컴파일 옵션 PACK_MATRIX_ROW_MAJOR를 쓰거나 CPU에서 전치하면 mul(v, M)이 됩니다.
뷰 행렬에서 카메라 위치는 어떻게 얻나요?수학
뷰 행렬은 월드→카메라. 역행렬은 카메라→월드이므로, 카메라 공간 원점을 역행렬로 보내면 월드의 카메라 위치이고, 이는 역행렬의 이동 성분(행우선이면 4행)입니다. 셰이더에서 mul(mInverseView, float4(0,0,0,1)).
파티클 수명 동안 크기 · 알파 · 색은 어떻게 바꿨나요?구현
t = Age/Life (0→1)로 정규화하고, 크기는 (1+2.5t)배, 알파는 min(5t,1)·(1−t)로 빨리 나타나 천천히 사라지게, 색은 주황→회색 lerp. 정규화된 t를 쓰면 수명이 달라도 같은 곡선을 재사용할 수 있고, 커브 에셋으로 바꾸기도 쉽습니다.
공기 저항 v *= (1 − k·dt)는 프레임레이트에 독립적인가요?수학
근사적으로만 그렇습니다. 정확한 해는 v·e^(−k·dt)이고 (1−k·dt)는 1차 테일러 근사라 dt가 작을 때 같습니다. dt가 1/k보다 커지면 부호가 뒤집히므로 max(…,0)으로 막았습니다. 정확히 하려면 expf(−k·dt)를 쓰거나 고정 시간 간격으로 적분합니다.
오브젝트 풀을 쓴 이유는?구조
발사마다 컴포넌트를 new/delete하면 할당 비용과 렌더리스트 등록/해제(벡터 재할당, 포인터 무효화 위험)가 생깁니다. 32칸을 미리 만들고 SetActive로 켜고 끄면 런타임 할당이 0이고, 개수 상한도 자연히 정해집니다. 꽉 차면 이번 발사의 일부만 생성됩니다.
판마다 머티리얼을 새로 만든 이유와 비용은?엔진
이 엔진은 상수(색 · 크기)를 머티리얼 객체가 갖고, 메쉬 에셋이 머티리얼 하나를 공유합니다. 공유 머티리얼을 바꾸면 같은 메쉬를 쓰는 모든 물체가 바뀝니다. 그래서 MakeMaterial로 인스턴스를 만들었습니다. 비용은 머티리얼당 리플렉션 · 버퍼 메모리와 아이템당 상수 버퍼 업데이트 · DrawCall. 많아지면 인스턴싱(인스턴스 버퍼에 색 · 크기)으로 바꿉니다.
DrawCall을 줄이려면?최적화
같은 머티리얼 · 메쉬를 인스턴싱(DrawIndexedInstanced)으로 묶고 인스턴스별 데이터는 인스턴스 버퍼나 StructuredBuffer로. 텍스처 아틀라스/배열로 텍스처 교체를 줄이고, 상태 변경이 적도록 정렬(셰이더 → 텍스처 → 블렌드). 더 많으면 GPU 파티클 + DrawInstancedIndirect.
소켓은 무엇이고 월드 변환은 어떻게 계산되나요?수학
메쉬 로컬 공간에 이름 붙인 위치 · 회전 · 크기. 자식은 부모 메쉬의 월드에 소켓 변환을 합성한 곳에 붙습니다. 크기 = 성분곱, 회전 = 부모 쿼터니언 × 소켓 쿼터니언, 위치 = 부모 위치 + Rotate(부모 회전, 소켓 위치 ⊙ 부모 크기). 데이터(JSON)라 재빌드 없이 튜닝할 수 있고, 아티스트가 DCC 툴에서 지정하기도 쉽습니다.
쿼터니언으로 벡터를 회전하는 식은? 오일러 대비 장점은?수학
v' = q · (0, v) · q* (q는 단위 쿼터니언, q*는 켤레). 짐벌락이 없고, 합성은 곱 하나, 보간(slerp)이 매끄럽고, 4개 값이라 저장이 작고 정규화로 누적 오차 보정이 쉽습니다.
점광원 감쇠식 1/(a + b·d + c·d²)의 각 항 의미는?조명
a(상수)는 가까울 때 무한대로 커지는 것을 막고, b(1차)는 완만한 감소, c(2차)는 물리적 역제곱 법칙. 게임에서는 물리값보다 보기 좋게 조합하고, Range를 넘으면 0으로 잘라 비용을 줄입니다.
파티클 성능 병목은 보통 어디인가요?최적화
정점 수보다 픽셀 채우기(fill-rate)와 오버드로입니다. 화면을 크게 덮는 반투명 판이 여러 장 겹치면 같은 픽셀을 여러 번 셰이딩하고 블렌딩합니다. 판 크기 · 개수 줄이기, 판 모양을 텍스처 외곽에 맞춘 폴리곤으로 자르기, 저해상도 버퍼에 그린 뒤 합성하기가 대책입니다.
소프트 파티클이란?심화
판이 지면이나 물체와 교차하는 곳에서 생기는 날카로운 직선을 없애는 기법. 픽셀 셰이더에서 씬 깊이 텍스처를 읽어 판 깊이와 차이를 구하고, 차이가 작을수록 알파를 줄입니다: α *= saturate((sceneDepth − particleDepth) / fadeDistance). 깊이 버퍼를 SRV로 읽을 수 있어야 합니다.
이번 작업에서 가장 어려웠던 점과 해결은?경험
(예시) 엔진에 파티클 기능이 없어 기존 메쉬 렌더 경로에 맞춰야 했던 점입니다. 렌더러 코드를 따라가 Priority 정렬, 머티리얼별 블렌드 · 깊이 상태, 리플렉션 기반 상수 버퍼 규칙을 확인하고, 엔진 수정 없이 게임 에셋(블렌드 상태 · 셰이더 · 머티리얼)만으로 구현했습니다. 또 공유 머티리얼 문제, 한글 소스 인코딩 문제(MSVC CP949 · fxc BOM)를 원인부터 찾아 해결했습니다.
